# Agent Note: Daily wall-clock tasks that start a Session unattended

Status: implemented

[English](2026-09-15-daily-wall-clock-scheduler.md) | 中文

## Problem

Harness 中没有任何东西会自行在一天中的某个时间开始工作。想要早晨分诊运行、每夜依赖检查或每周报告的人，必须亲自在机器前输入提示词，而这份工作的记录也只和其启动它的记忆一样持久。[harness 级 loop 决策](2026-07-16-harness-level-loop.zh.md)明确指出了这一缺口，并把基于时间的执行留给“调度器而非任一 goal 族”；[会话内 Schedule](2026-08-05-durable-web-schedule.zh.md) 包覆盖了相邻的场景——把提醒投递进一个活动对话——但它有意绝不自行创建会话，因此无法开始无人值守的工作。

有两个约束决定了答案。定时运行没有人盯着，因此审批请求会让它永远停住，而停滞的 Agent 会在进程的整个生命周期内占住其会话。工作还必须可见：配置它的用户需要看到时间、工作区、提示词，以及会话将运行的组合，这意味着需要一个配置界面而不是改文件。

## Decision

`@deepseek-ai/dsh-scheduler` 为每个已配置的每日任务挂载一个运行时，并在每次到点时在任务的工作区中创建一个普通根会话，把任务提示词作为其第一条消息送入，并在该轮次结束时释放 Agent。任务来自两层：插件的 `Config`（由部署或无界面运行提供），以及 `scheduler` 用户设置命名空间（由 Web 页写入，其提交值会替换随发布提供的列表）。

该插件不拥有任何持久调度状态。既没有补跑队列、没有错过的到点日志，也没有持久化的上次触发标记，因此不会有任何东西与实际运行所创建的会话产生偏差。`nextOccurrence` 严格解析到调用方 `now` 之后，这正是无补跑策略的实现方式：在某个到点之后才启动的进程会挂载下一次到点，而不是重放它睡过去的那一次。解析器不读时钟——`TaskRuntime` 在每次唤醒时传入 `Date.now()` 并重新推导目标——因此时钟调整或夏令时切换都无法留下过期目标。

任务校验按“进程运行期间什么会改变”来划分。任务的结构——其 id、挂钟时间、时区与星期——不会改变，因此 `validateTaskStructure` 在编写处就拒绝不可能成立的结构，而设置写入路径复用同一检查。任务引用的所有东西——工作区目录、权限预设与 Agent 预设名单——都可能改变，因此 `resolveArmedTasks` 在每次重新挂载时解析它们，并保留按任务的失败而不是让整个集合失败。若在写入时解析引用，一个被删除的目录会让整个挂载在下一次启动时被拒绝，因此这一划分是承重的而非风格选择。

定时运行必须使用审批策略为 `never` 的权限预设。无人在场应答请求，因此会询问的预设会在挂载时被拒绝，而不会被允许无限期停住运行。这是调度器约束配置而非仅校验配置的唯一之处。

`RUN_DEADLINE_MS` 把一次运行限制在一小时。由于每个任务已防止重叠，被永久占住的 Agent 会静默地让该任务的重复停摆，而不只是延迟它，因此该期限的存在是为了释放唯一的进行中槽位。提示词被接收之前的失败会回滚这个半配置的会话——解除工作区绑定并释放 Agent；接收之后的失败是该运行自身的持久结果，不会被回滚，因为记录才是读者要检查的东西。

`@deepseek-ai/dsh-client-ui-scheduler` 是设置页。它编辑本地草稿，并把整份任务列表作为一次原子变更提交，因为设置线路会整体替换数组，而逐键写入会发布半成品任务。每次保存都携带草稿起始时的 revision，因此来自另一界面的并发提交会被拒绝而不是被静默覆盖；被拒的保存保留编辑内容并采纳更新的 revision，以便重试能够落地。权限预设选择器从 Host 自身的命名空间 schema 中读取可用名称，而该 schema 是 Host 所声明常量的并集，因此不在客户端重述任何审批策略。

Host 行位于 Web 组合而非基础层。定时到点会从插件自身的上下文创建根会话，因此它需要 `agents`、`workspaceRegistry`、`sessionTitle` 与 `permissionPresets`；`workspaceRegistry` 是 Web 层的一行，而基础层服务的是没有 workspace registry 可注入的 TUI。随发布的 Web 行配置空任务列表，因此全新部署在用户添加任务之前不会调度任何内容。

## Alternatives considered

**带补跑的持久调度器。** 存储上次触发状态并重放进程未运行期间错过的到点，可以让调度跨重启存活。它需要在会话本身之外再引入第二套身份、持久化与恢复协议，并重新引出“过期任务是否仍应在数小时后运行”的问题。运行所创建的会话本身已经是记录，因此已发布设计保持这一唯一事实来源并跳过错过的时间。

**用 cron 表达式取代“每日时间加星期”。** 表达式表达力更强也更熟悉。它还需要一个解析器、一套校验词汇，以及针对一种语法的配置界面，而该功能的既定用途只是每日或工作日运行。每日 `HH:MM:SS` 加 `weekdays` 以保持纯粹且可测试的运算覆盖了该场景，而重复表达式仍是同一解析器可扩展的方向。

**扩展 Schedule 包而不是新增一个包。** Schedule 已拥有持久记录、重放与向活动会话的投递。让它创建会话会把两种不同的投递模型放进同一条持久流和同一组管理工具之下，而它的 fork 与冷会话语义关注的是提醒归属于某个对话，而不是开启新工作。

**进程外 cron 条目或操作系统调度器。** Host 的 crontab 条目可以在部署关闭时启动工作。它把配置移出产品，让运行在部署自身的存储中没有记录，也无法应用组合中的权限预设或 Agent 预设。进程内调度器把一次运行的每个事实都留在会话日志内。

**用持久化的上次触发标记来挂载，而不是重新推导。** 存储的目标无需重新计算即可跨重启存活。它也会在时钟或时区发生偏移的那一刻变得错误，并且需要自己的持久化与恢复。每次唤醒都从挂钟时间重新推导更便宜，且不可能过期。

## Consequences

只有在部署存活时到点才会到达，错过的时间就此消失；需要每个到点都执行的任务必须由持有持久队列状态的东西来调度。运行只在进程内，因此插件无法在部署关闭时启动工作。

该插件无法与交互式权限预设一起使用，这对任务能做的事是实实在在的削减：定时运行无法询问，因此任何环节需要人应答的工作流根本无法被调度。一小时期限是固定的而非按任务配置，停滞的运行会被取消而不会被报告。

没有任何东西会通知任何人某任务运行了或失败了。结果到达进程日志与所创建的会话，因此需要告警的部署必须去读它们，而不是等待一份报告。

## Testing

`tests/time.spec.ts` 固定到点解析：当天与次日的目标、对精确到点时刻的严格性、时区解读、跨到点的夏令时偏移变化、重叠中较早的瞬间、春令时跳变被跳过、星期选择，以及针对格式错误时间、空星期列表、越界星期与非整数时钟读数的拒绝。`tests/config.spec.ts` 固定结构与引用的分野：每一项结构拒绝、缺失的工作区目录以及占据该位置的文件、会询问的权限预设、依据名单是否存在而必填或拒绝的 Agent 预设、既不被挂载也不被报告的暂停任务，以及保持的挂载顺序。`tests/runtime.spec.ts` 用假定时器和被替换的会话事务驱动真实 `TaskRuntime`：每次到点恰好一次运行并带上该到点标记、终态结果日志、被容纳且保持挂载的启动失败、上一次运行进行期间被跳过的到点、进程未运行时错过的到点绝不被重放、星期挂载、释放静止，以及无法解析的时钟。`tests/session.spec.ts` 针对固定服务覆盖事务：有序的创建/绑定/配置/提示/释放路径、接收前对工作区与 Agent 的回滚、从未绑定时不解除绑定、接收后不回滚、已中止的信号，以及 `raceSettlement` 以 completed、timeout 或 aborted 结束。`tests/settings.spec.ts` 固定命名空间 schema、每天默认值、可用预设并集、无可用预设时的回退，以及必填字段。`tests/loader-composition.spec.ts` 从 `cordis.yml` 启动真实 Loader，证明函数插件命名空间完整到达、观察到设置分区安装及其存储列表校验，并固定 `Config` 默认值与不存在默认导出。

在客户端，`tests/locales.client.spec.ts` 固定词典对与命名空间拼写和 Host 声明的一致性，`tests/tasks-store.client.spec.ts` 覆盖草稿动作（含可选字段省略），`tests/controller.client.spec.ts` 覆盖镜像、revision 栅栏、被拒保存与重试，`tests/section.client.spec.tsx` 渲染该页并断言校验、缺失工作区标记与删除确认，`tests/apply.client.spec.ts` 在真实设置领域基座与 Remote 替身上挂载浏览器半边，断言注册、由 schema 推导的预设选择器、原子写入，以及释放时移除贡献。
